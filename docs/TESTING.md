# STermux 测试与验证规范

> 本文件定义 STermux 项目的测试体系、验证层级、测试约束、阶段验收要求与结果记录方式。  
> 本文件与以下文档配合使用：
>
> - `AGENTS.md`
> - `PROJECT_PLAN.md`
> - `PROJECT_STATUS.md`

---

## 1. 文档目标

STermux 是面向 Android Termux 环境的 Bash 项目。

项目开发主要在 Windows 与 Codex 环境中进行，但最终运行目标是 Android 手机上的 Termux。因此，项目必须建立清晰的分层测试体系，确保：

1. 能自动验证的功能尽量自动验证。
2. 能通过模拟环境验证的功能尽量增加模拟验证。
3. 涉及真实 Android 或 Termux 行为的功能必须经过实机验证。
4. 功能不能只因为代码已经写完就直接判定为已完成。
5. 项目进度状态必须与真实验证状态保持一致。

---

## 2. 测试总原则

STermux 采用三级验证体系：

```text
Level 1
本地自动测试

Level 2
Linux / 模拟 Termux 环境测试

Level 3
Android Termux 实机验证
````

总原则：

1. 能自动测试的功能，应优先自动测试。
2. 自动测试不能替代 Termux 专属功能的实机验证。
3. 模拟环境验证可以提升可靠性，但不能直接等同于 Android 实机结果。
4. 涉及用户真实数据的功能测试时，默认必须使用隔离测试目录。
5. 所有测试结果都应诚实记录，不得将“代码实现完成”直接写为“已完成”。

---

## 3. 验证状态定义

项目统一使用以下状态描述功能验证情况：

```text
未开始
开发中
代码实现完成
本地测试通过
模拟环境测试通过
待 Termux 实机验证
已完成
验证失败
已暂停
```

推荐状态流转：

```text
未开始
    ↓
开发中
    ↓
代码实现完成
    ↓
本地测试通过
    ↓
模拟环境测试通过
    ↓
待 Termux 实机验证
    ↓
已完成
```

说明：

- 纯逻辑类功能可以在本地测试通过后直接标记为已完成。
- Termux 专属功能必须经过实机验证后，才能标记为已完成。
- 若功能代码已经写完，但还未完成对应层级验证，应明确标记为“代码实现完成”或“待 Termux 实机验证”。

## 4. 测试目录与结构建议

项目应逐步建立测试目录：

```text
tests/
├── run_all.sh
├── test_config.sh
├── test_paths.sh
├── test_git.sh
├── test_extensions.sh
├── test_backup.sh
├── test_scheduler.sh
├── fixtures/
└── tmp/
```

说明：

- `tests/run_all.sh` 用于统一执行当前可用测试。
- `tests/test_*.sh` 根据项目阶段逐步增加。
- `tests/fixtures/` 存放测试用目录结构与模拟数据。
- `tests/tmp/` 或系统临时目录用于测试执行期生成的临时文件。

要求：

1. 不要在 Phase 1 一次性创建所有未来测试文件。
2. 当前阶段只为当前功能建立所需测试。
3. 所有测试脚本都要尽量保持可重复执行。

## 5. Level 1：本地自动测试

### 5.1 适用范围

适用于以下功能：

- Bash 脚本语法
- 配置读取逻辑
- 路径解析逻辑
- 用户输入解析
- 状态判断逻辑
- Git 流程逻辑
- 扩展选择逻辑
- 备份元数据逻辑
- 备份轮换逻辑
- 错误处理逻辑
- 回归检查

### 5.2 最低要求

每次新增或修改 Bash 文件后，必须执行语法检查：

```bash
bash -n manager.sh
bash -n core/*.sh
bash -n modules/sillytavern/*.sh
bash -n scripts/*.sh
bash -n tests/*.sh
```

要求：

1. 语法检查失败时必须先修复，再继续后续工作。
2. 不允许带着已知语法错误进入阶段验收。
3. 新增 Bash 文件必须纳入语法检查范围。

### 5.3 自动测试建议

当前环境允许时，应尽可能自动执行：

- 配置加载测试
- 默认值覆盖测试
- 路径存在性测试
- 用户输入解析测试
- 扩展编号选择测试
- 扩展策略判断测试
- 更新状态汇总测试
- 备份元数据生成测试
- 自动清理逻辑测试
- 错误返回路径测试

## 6. 测试 Fixture 规范

涉及 SillyTavern 目录结构的功能，优先使用测试 Fixture。

示例：

```text
tests/
└── fixtures/
    └── SillyTavern/
        ├── public/
        │   └── scripts/
        │       └── extensions/
        │           └── third-party/
        ├── data/
        ├── backups/
        └── config/
```

要求：

1. Fixture 应尽量模拟真实目录结构。
2. Fixture 中不得包含真实聊天记录、角色卡或私人数据。
3. Fixture 只用于测试，不作为生产目录使用。
4. 对目录结构有依赖的功能，优先在 Fixture 上完成自动测试。

---

## 7. Git 功能测试规范

### 7.1 适用功能

以下功能应尽可能使用本地临时 Git 仓库进行自动测试：

- SillyTavern 更新检测
- SillyTavern 更新执行
- 第三方扩展扫描
- 第三方扩展更新检测
- 选择性扩展更新
- 批量扩展更新
- 扩展“仅手动更新”策略
- 版本回退逻辑

### 7.2 建议场景

至少覆盖以下场景：

```text
本地已经最新
远程存在新 Commit
存在多个待更新 Commit
没有远程仓库
没有 upstream
git fetch 失败
git pull 失败
单个扩展更新失败
多个扩展同时存在更新
扩展被设置为 manual
```

### 7.3 必须验证的扩展逻辑

必须确认：

1. 一键更新全部时，不会更新 `manual` 状态扩展。
2. 用户手动选择时，仍然可以更新 `manual` 状态扩展。
3. 单个扩展更新失败时，其他扩展仍可继续更新。
4. 更新结果统计应正确区分成功、失败、跳过。

## 8. 备份功能测试规范

### 8.1 适用功能

- 手动备份
- protective 备份
- scheduled 备份
- catchup 备份
- 备份元数据生成
- 备份轮换
- 备份恢复
- 恢复前保护备份
- 备份失败处理

### 8.2 建议场景

至少测试：

```text
成功创建备份
正确生成 metadata
备份文件存在
备份文件大小大于 0
失败备份不会记录为 success
scheduled 自动轮换
protective 自动轮换
manual 不参与自动删除
恢复指定备份
恢复前自动创建保护备份
非法备份目录处理
不存在的备份处理
```

### 8.3 重要约束

1. 备份测试只能操作测试目录。
2. 自动测试不得清理真实用户备份目录。
3. 测试中涉及删除旧备份时，必须先验证目标路径属于测试路径。

## 9. Level 2：Linux 与模拟 Termux 环境测试

### 9.1 目标

Level 2 用于发现代码在 Linux 与拟似 Termux 路径结构下的兼容性问题。

它可以帮助暴露以下问题：

- 硬编码 Windows 路径
- 硬编码普通 Linux 用户目录
- 错误依赖 `/usr/bin`
- 错误假设 `/home/<user>`
- 未正确使用 `$HOME`
- 未正确使用 `$PREFIX`
- 路径带空格时处理失败
- Shell 环境差异导致的问题

### 9.2 建议模拟方式

条件允许时，可在 Linux 或 WSL 中设置临时环境变量，例如：

```bash
export HOME="/tmp/stermux-test/home"
export PREFIX="/data/data/com.termux/files/usr"
```

并在临时目录中模拟：

```text
/tmp/stermux-test/home/SillyTavern
```

### 9.3 结果解释

Level 2 只能说明：

- 脚本在 Linux 类环境下逻辑基本正确
- 路径处理较接近 Termux
- 代码没有明显依赖 Windows 专属路径

Level 2 不能说明：

- Android 后台调度一定正常
- Termux API 一定可用
- 实际手机环境一定与模拟结果一致

---

## 10. Termux 环境检测要求

涉及 Termux 专属功能时，应尽量通过实际环境判断。

可检查项包括：

- `$PREFIX`
- `uname`
- Termux 相关目录
- 命令是否存在
- `termux-job-scheduler` 是否可用
- `termux-wake-lock` 是否可用
- 其他 Termux API 命令是否存在

要求：

1. 不要只依赖单一环境变量作出全部判断。
2. “检测到 Termux 环境” 与 “检测到某个 Termux API 命令可用” 应分开判断。
3. 若专属命令不可用，应给出降级行为或明确提示。

## 11. Level 3：Android Termux 实机验证

### 11.1 必须实机验证的功能

以下功能最终必须进行手机实机测试：

- SillyTavern 实际启动
- 真实路径识别
- 真实 Git 更新
- 真实第三方扩展扫描
- 真实第三方扩展更新
- 真实用户数据备份
- 真实备份恢复
- 后台定时任务
- Termux 自动进入 STermux
- Shell 启动文件写入与移除
- Android 后台行为相关功能
- Termux API 相关功能

### 11.2 状态要求

若 Codex 当前无法执行实机测试，则必须标记为：

```text
待 Termux 实机验证
```

不得直接标记为：

```text
已完成
```

---

## 12. 实机测试输出格式

每个需要实机验证的功能完成后，必须给出明确测试步骤。

推荐格式：

```text
【Termux 实机测试】

测试目标：
验证 SillyTavern 启动功能

前置条件：
- 已安装 SillyTavern
- ST_PATH 已配置

执行步骤：
1. ...
2. ...
3. ...

预期结果：
1. ...
2. ...
3. ...

需要反馈的信息：
- 是否成功
- 终端输出
- 是否出现错误
- 与预期是否一致
```

规则：

1. 测试说明要具体到可直接照做。
2. 预期结果要足够清楚，便于判断是否通过。
3. 若测试失败，必须记录问题并重新修复后再验证。

## 14. 阶段测试矩阵

每个 Phase 完成时，必须生成测试矩阵。

推荐格式：

```text
| 功能        | 本地测试     | 模拟环境 | Termux 实机 | 状态               |
| ----------- | ------------ | -------- | ----------- | ------------------ |
| 配置读取    | 通过         | 不需要   | 不需要      | 已完成             |
| ST 路径检测 | 通过         | 通过     | 待测试      | 待 Termux 实机验证 |
| ST 启动     | 基础检查通过 | 通过     | 待测试      | 待 Termux 实机验证 |
```

阶段总结中必须明确说明：

1. 哪些功能已经完全验证
2. 哪些功能仅通过自动测试
3. 哪些功能仍等待实机验证

---

## 15. 阶段验收与验证关系

如果当前 Phase 存在待实机验证功能，阶段状态可写为：

```text
开发完成，待实机验收
```

此时不应写为：

```text
已完成
```

阶段流程建议：

```text
开发
    ↓
步骤级自检
    ↓
本地自动测试
    ↓
模拟环境测试
    ↓
生成 Termux 测试步骤
    ↓
用户实机验证
    ↓
修复发现的问题
    ↓
重新验证
    ↓
更新 PROJECT_STATUS.md
    ↓
阶段成果总结
    ↓
用户确认
```

## 16. 自动测试安全原则

自动测试必须遵守以下规则：

1. 默认使用测试目录或临时目录。
2. 不修改用户真实 SillyTavern 数据。
3. 不删除用户真实备份。
4. 不操作真实聊天记录。
5. 不依赖真实第三方扩展仓库。
6. 可以使用本地临时 Git 仓库模拟远程更新。
7. 测试结束后应清理自身创建的临时数据。
8. 清理失败不能影响用户真实目录。
9. 无法确认当前目录为测试目录时，禁止执行危险删除操作。
10. 自动测试不得复制、读取、`source` 或使用项目真实的 `config/user.conf`。
11. 测试项目的 `user.conf` 必须由测试自身在隔离目录创建为空文件或生成专用测试配置。
12. 自动测试不得启动真实 SillyTavern；涉及启动的测试只能调用测试 Fixture 中的 `start.sh`。
13. 管理器集成测试必须设置违规启动哨兵，证明来源用户配置中的真实或仿真绝对 `ST_PATH` 不会被访问。
14. SillyTavern 安装测试不得访问真实网络或调用真实 `pkg`，只能使用 Mock 软件包命令与本地临时 Git 仓库。
15. 安装成功、失败、目录冲突和残留目录测试只能写入当前测试临时根目录。
16. STermux 自更新测试不得修改真实项目仓库、访问 GitHub 或真实执行 `manager.sh` 重启，必须使用临时 Git 仓库和重启 Mock。
17. 第三方扩展测试不得复制真实 `extension-policy.conf`，不得扫描或更新真实 SillyTavern 扩展；策略、扩展目录与 Git 远程必须全部由测试在临时根目录创建。

## 17. 测试隔离要求

建议测试环境统一使用：

```text
tests/tmp/
```

或系统临时目录，例如：

```text
/tmp/stermux-test-<random>
```

危险操作前必须确认：

1. 目标路径非空
2. 目标路径位于允许的测试根目录
3. 目标路径不等于 `$HOME`
4. 目标路径不等于 `/`
5. 目标路径不等于 `ST_PATH`

配置隔离还必须确认：

1. 隔离项目没有从来源项目复制 `config/user.conf`。
2. 隔离项目的 `config/user.conf` 由测试创建。
3. Fixture 的 `ST_PATH` 位于当前测试临时根目录内。
4. 即使来源 `config/user.conf` 保存了有效的绝对 SillyTavern 路径，测试也不会读取、访问或启动该路径。

任何测试脚本执行删除前，都应先进行路径安全校验。

## 19. 可选远程实机测试能力

未来可以考虑通过 SSH 连接 Android Termux，实现更高程度的自动化实机测试。

可能流程：

```text
Codex 编写代码
    ↓
Git 提交
    ↓
手机 Termux 获取最新代码
    ↓
真实 Termux 执行测试
    ↓
返回测试日志
    ↓
Codex 分析结果
```

该能力属于后续增强项。

V1 不要求实现自动 SSH 测试框架。

## 20. 最终验证原则

STermux 的验证原则总结如下：

```text
能自动测试的
尽量自动测试

能模拟验证的
尽量增加模拟验证

依赖真实 Android 的
必须实机验证
```

Codex 必须严格区分以下状态：

```text
代码实现完成
自动测试通过
模拟环境通过
Termux 实机验证通过
```

四者含义不同，不能混用。

只有完成当前功能所需的验证层级后，才能将该功能标记为：

```text
已完成
```

---

## 21. 对 Codex 的直接要求

在 STermux 项目中，Codex 必须遵守以下测试要求：

1. 完成修改后，优先执行当前环境可执行的最高级别验证。
2. 能自动测试的功能，不得只依赖人工目测检查。
3. Termux 专属功能未经实机验证，不得写为“已完成”。
4. 无法执行实机验证时，必须明确标记为“待 Termux 实机验证”。
5. 自动测试必须使用隔离测试目录。
6. 阶段成果总结必须附带测试矩阵。
7. 用户实机测试失败后，必须记录问题、修复并重新验证。
8. `PROJECT_STATUS.md` 中的状态必须与真实验证结果一致。

- 不包含失效的旧规则

## 24. 当前建议的最低执行标准

在项目早期阶段，至少应做到：

### Phase 1

- Bash 语法检查
- 配置与路径逻辑的基础测试
- ST 启动功能的 Termux 实机验证

### Phase 2

- Bash 语法检查
- Git 更新逻辑自动测试
- ST 更新功能的 Termux 实机验证

### Phase 2.5

- Bash 语法检查
- 未安装/已有安装菜单分流测试
- 依赖缺失、可用及命令损坏三态测试
- Mock `pkg` 与本地临时 Git 仓库安装流程测试
- 目标目录冲突、失败隔离和 `ST_PATH` 保存测试
- 纯净 Termux 设备真实从零安装与首次启动验收

### Phase 2.6

- Bash 语法检查
- 临时 Git 仓库状态、fetch 与 `pull --ff-only` 测试
- tracked 程序修改、分叉、无 upstream 和 detached HEAD 拒绝测试
- fetch、pull 与重启失败隔离测试
- Android Termux 真实 STermux 自更新和自动重启验收

### Phase 3

- 扩展扫描与策略逻辑自动测试
- 扩展更新流程自动测试
- 非 Git、无 upstream、fetch/pull 失败及单项失败继续测试
- 单选、多选过滤去重、批量跳过仅手动扩展测试
- 中文、空格路径及空扩展目录测试
- 扩展更新功能的 Termux 实机验证

### Phase 4

- 备份创建与恢复自动测试
- 备份目录安全校验
- 真实备份与恢复的 Termux 实机验证

### Phase 5

- 定时任务逻辑测试
- 轮换逻辑测试
- 逾期补偿测试
- 定时备份的 Termux 实机验证

后续 Phase 在各自开始时继续扩展相应测试。
